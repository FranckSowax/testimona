## 1. Ce qu'est le produit aujourd'hui

**Concept d'origine (TdR)** : plateforme sociale publique de mémoire des défunts. Un utilisateur écrit un
témoignage → la « page RIP » du défunt est créée automatiquement (ou rattachée si elle existe) → les
*close relatives* l'administrent façon Wikipedia → photos, dons, détails de vie, funérailles.

**Ce qui a été construit (~35 000 lignes TS/TSX, 1 app Next.js)** :

| Domaine | État | Écart au TdR |
|---|---|---|
| Page mémorielle (5 onglets + boutique) | ✅ riche | Conforme, + boutique ajoutée |
| Témoignages (like / commentaire / report / modération) | ✅ | Création via **bouton + modale**, pas le formulaire unifié « Write a testimonial » qui crée la page |
| Photos (likes, commentaires, report, story viewer) | ✅ | Pas de témoignage texte+photo (T8 différé) |
| Co-propriétaires (`MemorialMember`, invitations) | ✅ | **Pas de preuve de lien de parenté** (acte de naissance…) |
| Dons Stripe Checkout + webhook + e-mails Resend | ✅ | **Aucun payout** vers les ayants-droit (G4) |
| Notifications, My Testimonials, profil, favoris | ✅ | Notifications calculées à la lecture (pas de table `Notification`) |
| Recherche + suggestions dès 3 lettres | ✅ | Pas de dédoublonnage nom/pays/date de décès |
| **Hors TdR** : clips vidéo IA (fal.ai Kling / Higgsfield), visuels IA, crédits utilisateurs, solde « Studia », boutique (t-shirts, pagnes, cercueils…), espaces pub, back-office admin complet | ✅ | Ajouts successifs non prévus dans le cahier des charges |

**Constat produit** : le cœur promis par le TdR (« un témoignage crée la page », vérification des ayants-droit,
reversement des dons) est **le moins abouti**, alors que des modules périphériques monétisés (IA vidéo,
crédits, boutique, pub) ont été développés. C'est le principal argument pour une refactorisation *du concept*.

## 2. Diagnostic technique

### Stack
Next.js 15 (App Router, Server Actions) · React 19 · Tailwind v4 · Supabase (Postgres/Auth/Storage) · Stripe ·
Resend · Sentry · next-intl FR/EN · GSAP · Railway (Nixpacks) · pnpm 9 + Turborepo.

### Points solides
- Découpage App Router lisible (`(public)`, `(auth)`, `(dashboard)`, `(admin)`), i18n complète.
- Webhook Stripe correct (signature vérifiée, statuts Succeeded/Failed/Refunded).
- Contrôle d'accès « gestionnaire » centralisé (`lib/memorial/access.ts`).
- Design system V2 documenté (tokens, ~36 composants, a11y travaillée).

## 3. Pistes de refactorisation du concept

Trois directions possibles — **à arbitrer avant tout code** (voir §5).

### Option A — Recentrage « mémoire sociale » (fidèle au TdR)
Le témoignage redevient l'entrée unique. On livre le cœur manquant, on gèle/sort le périphérique.
- Formulaire unifié « Write a testimonial » → matching doublons (nom + pays + mois/année, âge en fallback) → création auto de la page.
- Vérification des *close relatives* (upload de preuve, file de validation admin).
- Payout des dons aux ayants-droit vérifiés (Stripe Connect Express).
- Modules IA vidéo / crédits / Studia / pub **désactivés derrière feature flags** (pas supprimés).

### Option B — « Mémorial premium » (monétisation assumée)
On garde la boutique, les clips IA et les crédits comme proposition de valeur, mais on les restructure en
modules propres (facturation unifiée, un seul système de crédits, un seul provider IA).

### Option C — Plateforme « funérailles » (B2B2C)
Pivot vers les familles + prestataires (pompes funèbres, imprimeurs, partenaires boutique) : la page
devient l'outil d'organisation (funérailles, contributions, marchandises), le social passe au second plan.

Recommandation : **A**, car c'est le seul concept qui correspond au cahier des charges validé et les points
bloquants de la recette (G4 payout, T5-T8 témoignage) en font partie. B et C peuvent se greffer ensuite sur
une base saine.

## 4. Socle technique à poser avant (quel que soit le concept)

1. **Recloner le dépôt Git** et travailler sur une branche `refactor/…` (l'archive actuelle n'a pas d'historique).
2. **Migrations Supabase versionnées** : `supabase init` + baseline `db dump` de la prod → `supabase/migrations/`. Supprimer `packages/database` (Prisma mort).
3. **Types générés** : `supabase gen types typescript` → `packages/shared/src/database.types.ts`, clients typés `SupabaseClient<Database>`.
4. **Couche domaine** `apps/web/src/server/<domaine>/` (memorial, testimonial, photo, donation, member…) : repositories + services, seuls autorisés à toucher la base. Les pages/actions n'appellent plus `.from()`.
5. **Inversion de la sécurité** : client utilisateur (RLS) par défaut ; *service-role* réservé à une liste fermée (webhooks, admin, jobs) ; RLS + policies sur 100 % des tables, vérifiées par `supabase db lint`/advisors en CI.
6. **Tests** : Vitest sur services domaine (accès, dons, matching doublons) + tests de policies RLS ; CI bloquante (retirer `continue-on-error`).
7. **Nettoyage** : retirer le bouton de don simulé en prod (flag `NODE_ENV`/env dédiée), `docker-compose.yml` legacy, variables Cloudinary.
8. **Feature flags** simples (`lib/flags.ts` lu depuis l'env) pour isoler clips IA / boutique / pub.

## 5. Décisions à prendre (bloquantes)

1. **Direction concept** : A (recentrage TdR), B (premium), C (B2B2C funérailles) ou autre ?
2. **Sort des modules hors TdR** (clips IA, crédits/Studia, boutique, pub) : flag off, conserver, supprimer ?
3. **Payout** : Stripe Connect vers un ayant-droit vérifié, ou reversement manuel par Testimona (comme le suggère la note 1 du TdR) ?
4. **Vérification des close relatives** : preuve documentaire + validation humaine, ou déclaratif + co-validation par la famille ?
5. **Données existantes** en prod : à conserver (migration) ou base repartie de zéro ?
